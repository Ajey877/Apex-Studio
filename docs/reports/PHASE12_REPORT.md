| 11 | **Mode semantics** | `off` — nothing captured (playback untouched; `off` does **not** mute playback, documented in UI + code). `read` — default, nothing captured, playback exactly as before. `write` — from arm to pass end every transport step samples the live control value, replacing the lane inside the pass. `touch` — the pass starts at the grab and closes on release; outside `[grab, release]` the previous lane is preserved exactly, so the original curve resumes. `latch` — the last touched value keeps writing after release until the transport boundary. Arming is from the transport (a recording lane records when the playhead is inside its clip); one lane at a time, because a pass records exactly one target. |
| 12 | **Undo / persistence** | `automationClipWithRecordedPass` returns the **same clip object** when a pass changes nothing → no history entry, no autosave, no resync (so TOUCH with no movement is silent). A real pass replaces only `[startX, endX]`, preserves every point outside it, renders seam discontinuities as `STEP_X = 1e-4` step-pairs, collapses coincident points keeping the later one, prunes only redundancy it introduced, and returns a ≥2-point ascending lane. The commit is one `mutateProjectState(..., 'Record automation pass (<label>)')`, i.e. **one logical undo**; no per-pointer-move entry exists because updates arrive through `isContinuous` batching, which the pass commit flushes. Undo/redo restore the exact prior/recorded arrays; save→reopen round-trips them unchanged (mode map omitted when all READ). |

| 17 | **Known limitations** | (1) `master_vol` cannot be recorded — it is engine-owned and has no project-state value to read back, so `readAutomationTargetValue` returns `null` and `canRecordTarget` excludes it. (2) VST3 lanes record **committed** values only: the native editor is draft-then-Apply and the host never observes the plug-in's own knob movements before Apply. (3) One target records at a time; overlapping recording lanes arm sequentially on later ticks. (4) There is no loop *region* in the product, so a "loop" is Pattern-Mode wrap or a seek — a pass never spans either, by design. (5) No MIDI-CC lane recording, no new LFO authoring, no tempo-relative redesign — all explicitly out of scope. (6) No interactive/physical QA was performed in this environment; audio assertions are AudioParam-schedule measurements, not acoustic output. |
